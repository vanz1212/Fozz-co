Arsitektur Pembayaran Real-Time & Skema Sistem

Spesifikasi teknis penyelesaian transaksi Payment Gateway, validasi otomatis instrumen QRIS Dinamis & Virtual Account, serta trigger atomik database PostgreSQL.

Siklus Penyelesaian Transaksi Real-Time Tanpa Intervensi Manual

Pada perilisan drop streetwear limited edition, kecepatan dan kepastian inventaris adalah prioritas utama. Sistem menggunakan arsitektur Asynchronous Webhook Settlement yang menghubungkan perbankan nasional, Payment Gateway, dan backend FOZZ dalam hitungan sub-detik (< 800ms) dengan verifikasi tanda tangan kriptografis HMAC-SHA512.

1
Checkout & Token Inisiasi

Customer checkout, record terbit di tabel orders dengan status Pending (TTL 15 menit). Backend FOZZ meminta token tagihan via POST /v1/charge ke Payment Gateway.

2
Generate Token & Payload

Gateway berinteraksi dengan Switch Perbankan (ASPI / Core Banking) untuk menerbitkan QRIS Dinamis (EMVCo Single-Use) atau nomor Virtual Account unik dengan nominal terkunci.

3
Real-Time Standby & Push

Browser customer menampilkan QR / nomor VA dan membuka saluran listening (WebSocket / Server-Sent Events / Long Polling) untuk mendeteksi event pelunasan tanpa perlu refresh halaman manual.

4
Eksekusi Nasabah & Clearing

Customer memindai QRIS via m-banking / e-wallet atau mentransfer ke Virtual Account. Jaringan perbankan (BI-FAST / GPN / Switch) memvalidasi saldo dan menyelesaikan kliring dana seketika.

5
Webhook Callback & Crypto

Gateway menembakkan HTTP POST ke endpoint FOZZ (/api/webhooks) membawa header X-Signature: HMAC-SHA512. Backend memverifikasi otentisitas payload dan mencegah duplicate replay.

6
Atomic Trigger & UI Sync

Status pesanan bergeser ke Paid dalam transaksi database atomik. Trigger PostgreSQL seketika memotong stok product_sizes dan UI customer otomatis berganti status Paid.

Zero-Trust Signature & Idempotensi

Setiap payload webhook divalidasi dengan formula:
SHA512(order_id + status_code + gross_amount + ServerKey) Jika signature berbeda 1 bit saja, request ditolak HTTP 401. Setiap request juga diperiksa terhadap idempotency_key untuk mencegah pemotongan stok ganda akibat webhook retry.

Proteksi Race Condition & Concurrency

Saat drop langka diperebutkan ribuan user, backend menerapkan Row-Level Locking (SELECT ... FOR UPDATE). Jika user tidak melunasi dalam 15 menit (TTL expired), background worker otomatis membatalkan order dan mengembalikan alokasi kuota ke etalase publik.

Standar EMVCo & ASPI: Mengapa QRIS Dinamis Otomatis 100% Anti-Distorsi?

Berbeda dengan QRIS Statis (cetakan stiker) yang mengharuskan pembeli mengetik nominal sendiri secara manual (rentan salah transfer atau manipulasi bukti transfer palsu), QRIS Dinamis (Point of Initiation Method = 12) mengunci nominal tagihan pesanan, invoice ID, dan checksum integritas data ke dalam kode QR unik yang langsung terbaca oleh aplikasi mobile banking / e-wallet mana pun di Indonesia.

Bagaimana Settlement Berjalan Otomatis?

Ketika customer menekan "Konfirmasi Bayar" di aplikasi mobile perbankan (BCA Mobile, Livin Mandiri, GoPay, OVO), switch ASPI meneruskan dana ke escrow Payment Gateway. Dalam waktu < 1 detik, gateway membunyikan webhook callback ke server FOZZ. Karena payload memuat order_id yang presisi, sistem tidak membutuhkan mutasi rekening bank manual atau upload struk kertas.

Prinsip Closed/Fixed Amount Virtual Account & Core Banking Switching

FOZZ.CO mengimplementasikan Closed Virtual Account (Fixed VA) yang secara eksklusif dikaitkan dengan satu nomor pesanan dan satu jumlah tagihan pasti. Core banking switch menolak transfer jika nasabah memasukkan nominal yang tidak sesuai, menjamin akurasi rekonsiliasi 100%.

Anatomi Nomor 16-Digit Virtual Account:

[88012] - [08123456789] Digit 1 - 5: Company Identification Prefix (BCA: 88012, Mandiri: 89901, BRI: 10234, BNI: 98811). Digit 6 - 16: Unique Customer / Order Identifier yang di-generate sistem secara idempotent.
Mekanisme Inquiry & Payment (BI-SNAP):
1. Phase Inquiry: Saat nasabah memasukkan VA di ATM/m-banking, bank mengirimkan API Inquiry ke Gateway. Gateway mengembalikan nama penerima (FOZZ - NAMA NASABAH) dan total harga pasti.
2. Phase Payment Notification: Begitu dana didebit, Core Banking memancarkan notifikasi ISO 8583 / REST JSON ke gateway yang langsung memicu webhook ke server FOZZ.

4 Lapisan Validasi Otomatis Webhook Virtual Account:

  1. Verifikasi Tanda Tangan: Menghitung ulang hash HMAC-SHA512 dari order_id + status_code + gross_amount + server_key untuk memastikan request benar-benar berasal dari aggregator perbankan, bukan penyerang luar.
  2. Idempotency Lock: Menyimpan transaction_id ke dalam cache database. Jika bank mengirim callback berulang (karena network latency retry), callback kedua langsung direspons HTTP 200 tanpa memproses ulang transaksi.
  3. Cross-Check Nilai Tagihan: Memverifikasi bahwa gross_amount callback cocok 100% dengan orders.total_harga.
  4. Commit Transaksi Atomik: Menjalankan fungsi SQL transaksional untuk memindahkan status pesanan ke 'Paid' dan memicu pemotongan inventaris secara langsung.

Trigger Atomik Pemotongan Stok (Zero Overselling Guarantee)

Saat checkout, record induk otomatis tercatat di orders untuk mengikat data tagihan dan logistik. Rincian artikel diproteksi di order_items dengan harga terkunci (anti-distorsi harga). Begitu webhook payment gateway memverifikasi pelunasan dan mengubah status pesanan ke Paid, trigger atomik PostgreSQL seketika memotong kuota di product_sizes.

-- Trigger Otomatis Pemotongan Stok saat Settlement Berhasil
CREATE OR REPLACE FUNCTION deduct_stock_on_order_paid()
RETURNS TRIGGER AS $$
BEGIN
  IF (NEW.status_pesanan = 'Paid' AND OLD.status_pesanan = 'Pending') THEN
    UPDATE product_sizes ps
    SET stok = ps.stok - oi.jumlah
    FROM order_items oi
    WHERE oi.order_id = NEW.id
      AND ps.product_id = oi.product_id
      AND ps.ukuran = oi.ukuran;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
